# Монетизация: анализ проекта и план перехода на платные подписки

Документ описывает, что в текущем продукте уже годится для продажи, чего в коде не хватает,
как встроить биллинг без переписывания доменов и какие метрики это позволит измерять.

## 1. Что уже есть в продукте

| Блок | Реализация | Ценность для монетизации |
|---|---|---|
| Трекинг привычек и отметки | `backend/src/habits/` | ядро продукта, база бесплатного тарифа |
| Стрики: текущий, рекорд, истечение | [`calc_streaks`](../backend/src/habits/service.py:22), поля `current_streak_days`, `max_streak_days`, `streak_expires_at` | главный источник эмоции и поводов для апселла |
| Аналитика и графики | [`analytics/service.py:26`](../backend/src/analytics/service.py:26), plotly-JSON (heatmap, bar, radar) | платный слой: глубина и период |
| Социальный слой: друзья, лента, пуши/шеймы | `backend/src/friends/`, `backend/src/feed/`, `backend/src/social/` | сетевой эффект, удержание |
| Чат в реальном времени | [`social/ws.py`](../backend/src/social/ws.py:70) | удержание, не гейтить |
| Достижения | `backend/src/achievements/` (10 штук) | бесплатно, как крючок вовлечения |
| Экспорт CSV | [`exports/router.py:24`](../backend/src/exports/router.py:24), две ручки | естественный Pro-функционал |
| Telegram-уведомления | [`notifications/scheduler.py`](../backend/src/notifications/scheduler.py:16) | канал апселла и Pro-фича |

Вывод: продукт уже содержит три независимых источника ценности — трекинг, социальный слой,
аналитику. Монетизировать нужно **объём и глубину**, а не доступ к базовому функционалу.

## 2. За что платить и кому

| Сегмент | Боль | Что продаём |
|---|---|---|
| Дисциплинированный одиночка | «Хочу видеть прогресс за год, а не за месяц» | история за всё время, сравнение периодов, экспорт |
| Пары и друзья | «Хочу, чтобы партнёр видел и подталкивал» | совместные привычки без ограничения партнёров, общий стрик |
| Публичные челленджи, блогеры | «Нужно показать результат» | PDF/CSV отчёт, бейджи, публичный профиль |

Не платят за: регистрацию, чат, друзей, ленту, достижения. Эти функции создают удержание
и приводят новых пользователей — их ограничение сокращает воронку, а не выручку.

## 5. Архитектура биллинга

Отдельный домен `backend/src/billing/` по правилам проекта:
`router.py → service.py → repository.py`, плюс `models.py`, `schemas.py`, `enums.py`.

### Таблицы

| Таблица | Ключевые поля | Назначение |
|---|---|---|
| `plans` | `code`, `price`, `period`, `features` (jsonb) | справочник тарифов |
| `subscriptions` | `user_id`, `plan_code`, `status`, `current_period_end`, `auto_renew`, `provider`, `external_id` | текущая подписка |
| `payments` | `subscription_id`, `amount`, `currency`, `status`, `provider_payment_id` | история платежей |
| `payment_events` | `provider_event_id` **unique**, `payload` | журнал вебхуков для идемпотентности |

Статусы подписки: `trialing`, `active`, `past_due`, `canceled`, `expired`.

### Проверка прав

1. `EntitlementsService.get(user_id) -> Entitlements` — единая структура прав:
   `max_habits`, `history_days`, `export_enabled`, `reminders_limit`, `max_partners`.
2. Кэш в Redis на 5 минут: тариф меняется редко, а проверяется на каждом создании привычки.
3. Зависимость `CurrentEntitlementsDep` рядом с `CurrentUserIdDep` в
   [`auth/deps.py`](../backend/src/auth/deps.py:1).
4. Проверка **в сервисе**, а не в роутере: `HabitsService.create()` зовёт `ensure_habit_limit()`.
   Так правило действует и для API, и для фоновых задач.
5. Превышение — своё исключение `PlanLimitExceeded`, роут переводит его в
   **402 Payment Required** с телом «какой лимит и как его снять». Фронт получает готовый
   триггер для paywall-модалки.
6. Права **не кладём в JWT**: токен живёт 7 дней, подписка может закончиться раньше,
   и пользователь неделю останется Pro.

### Платежи

Сценарий: `POST /billing/checkout` создаёт платёж и отдаёт ссылку на оплату; провайдер присылает
вебхук; обработчик проверяет подпись, пишет событие в `payment_events` (уникальный
`provider_event_id` защищает от повторной обработки) и в той же транзакции обновляет подписку.
Провайдеру отвечаем быстро, тяжёлую часть (уведомление в Telegram) выносим в фоновую задачу.

Grace period: 3 дня в статусе `past_due`, затем автоматический откат на Free.

Провайдеры: YooKassa или Tinkoff (РФ, рекуррентные платежи). Для продаж внутри Telegram-бота
альтернатива — Telegram Stars: снимает вопросы с чеками и возвратами на старте.

### API

| Метод и путь | Назначение |
|---|---|
| `GET /api/v1/billing/plans` | список тарифов и цен |
| `GET /api/v1/billing/subscription` | текущая подписка и её срок |
| `POST /api/v1/billing/checkout` | начать оплату |
| `POST /api/v1/billing/webhook` | приём событий провайдера |
| `GET /api/v1/billing/payments` | история платежей |

## 6. Что починить, чтобы Pro-функции масштабировались

1. **Напоминания.** Вынести APScheduler в отдельный процесс под `pg_advisory_lock`.
   Две реплики бэкенда сейчас дадут двойные сообщения — для платной функции это возвраты.
2. **WebSocket.** Реестр соединений → Redis pub/sub, тогда чат и пуши работают при любом
   числе инстансов.
3. **Аналитика.** Кэш дашборда на 60 секунд и материализованное представление по `habit_logs`
   для годовых срезов (в демо-базе уже ~535 тыс. строк логов).
4. **Лимиты без `COUNT(*)`.** Счётчик привычек в Redis или поле в `subscriptions`,
   инкремент при создании и удалении.
5. **Rate limiting по тарифу** (Redis token bucket), иначе один скрипт на Free положит API.

## 7. Метрики

**North Star:** количество отметок привычек в неделю у активных пользователей (WAC) —
прямо отражает ценность продукта и уже есть в `habit_logs`.

Воронка: `регистрация → первая привычка → первая отметка (D1) → 7 дней подряд →
показ paywall → начало оформления → оплата → продление`.

Метрики: конверсия Free→Pro по когортам, trial→paid, churn, ARPU, LTV = ARPU / churn,
payback привлечения, retention D1/D7/D30, выживаемость стрика (доля доходящих до 7/21/30 дней).

Что считается уже сейчас: retention и стрики — по `habit_logs`; социальная активность —
по `messages`, `user_relations`, `reviews`.

Чего не хватает: таблицы `events` (`user_id`, `name`, `props` jsonb, `created_at`).
Без неё не измерить показы paywall и конверсию, а значит нельзя проверить тарифную сетку.

Естественные триггеры апселла:
- упёрся в лимит 5 привычек;
- попытка выгрузить CSV;
- стрик 7 дней («не потеряй прогресс — открой годовую историю»);
- попытка позвать третьего друга в совместную привычку.

| Срок | Объём | Результат |
|---|---|---|
| Неделя 1 | домен `billing`, планы, `Entitlements`, лимит привычек, гейт CSV, индикатор тарифа в UI | платный слой виден и работает без платежей |

| Далее | Telegram-дайджест для Pro, группы до 5, годовой PDF-отчёт | рост ARPU |

## 9. Риски

- **Юридика.** Платёжка требует ИП или самозанятости, публичной оферты и чеков по 54-ФЗ.
  Telegram Stars снимает часть боли, но берёт комиссию.
- **PCI DSS.** Карточные данные не храним и не передаём через свой бэкенд — только у провайдера.
- **Идемпотентность вебхуков.** Самая дорогая ошибка в биллинге: повторный вебхук без
  уникального `provider_event_id` создаёт вторую подписку или второй платёж.
- **Обрезание уже показанных данных.** Забирать историю задним числом — прямой путь к отпискам;
  ограничивать надо на входе, а не отнимать показанное.

## 10. Короткая версия для питча

> Монетизация строится на глубине аналитики и социальных функциях, а не на доступе к базовому
> трекингу: Free — 5 привычек и 30 дней истории, Pro — без ограничений и экспорт, Team —
> групповые привычки. Технически это отдельный домен `billing` с entitlements-сервисом и
> лимитами на уровне сервисов; платежи — через вебхуки провайдера с идемпотентностью по id
> события. Метрики считаем по `habit_logs`, которых у нас уже полмиллиона.
