# Справочная часть (не рассказывать вслух)

## Что это за проект

Социальная сеть для совместного трекинга привычек — `analogovnet.rest`.
Идея: одиночные трекеры бросают, потому что прогресс видит только сам человек.
Здесь привычка становится постом в ленте, друзья реагируют, стрик виден, есть общие привычки.

## Что умеет продукт

| Блок | Что есть |
|---|---|
| Аккаунт | регистрация, вход по логину и паролю, access-токен JWT и refresh-токены в БД, профиль, смена пароля, удаление аккаунта |
| Аватарки | загрузка через presigned URL в S3-совместимое хранилище (MinIO), дефолтные картинки |
| Привычки | создание, редактирование, удаление, цвет, видимость (только я / друзья / все), дата старта, до трёх напоминаний, отметка выполнения, снятие отметки |
| Стрики | текущий стрик, рекорд, срок истечения стрика, пересчёт при отметке — на бэкенде |
| Аналитика | сводка (лучший стрик, выполнено сегодня, стабильность, всего привычек), детали по каждой привычке (процент выполнения, заброшенные), активность по дням и дням недели, готовые plotly-графики |
| История | журнал отметок с фильтром по произвольному диапазону дат |
| Друзья | заявки, принятие, удаление, блокировки, поиск пользователей, лидеры по стрикам |
| Лента | привычки и отметки друзей как посты, реакции «пуш» (поддержка) и «шейм» (пристыдить), комментарии |
| Чат | личные сообщения в реальном времени по WebSocket, история, статусы прочтения, несколько вкладок |
| Достижения | 10 штук: за 1/3/10 привычек, за 3/7/21/30 дней стрика, за 1/5/15 друзей |
| Telegram | привязка аккаунта по одноразовой ссылке, напоминания по расписанию, webhook |
| Экспорт | два CSV: сводка по привычкам и журнал отметок, с выбором разделителя |

## Как устроено технически

- **Backend**: Python 3.12, FastAPI, SQLAlchemy 2 (async) + asyncpg, PostgreSQL 16, Alembic (14 миграций), Pydantic 2, Poetry.
- **Слои в каждом домене**: `router.py` (HTTP) → `service.py` (правила) → `repository.py` (SQL), плюс `schemas.py` и `models.py`.
- **Домены**: `users`, `habits`, `friends`, `social` (чат), `feed`, `analytics`, `achievements`, `exports`, `telegram`, `auth`.
- **Frontend**: React 19, Vite, TypeScript, TanStack Query, Tailwind + shadcn/ui; клиент API генерируется из OpenAPI (orval), поэтому типы совпадают с бэкендом.
- **Инфраструктура**: Docker Compose из четырёх контейнеров — Postgres, MinIO (плюс разовый контейнер инициализации), backend и frontend на Caddy. Миграции применяются автоматически при старте backend.
- **Цифры**: 33 эндпоинта в API, 10 достижений, 16 тестов. Демо-база: около 2,8 тыс. пользователей, 13 тыс. привычек, 535 тыс. отметок, 95 тыс. сообщений.

## Зачем это знать

На любой вопрос «а как у вас…» ответ должен опираться на этот список: сначала что умеет
продукт, потом где это в коде. Если чего-то в списке нет — значит этого нет, и так и говорим.

# Часть 3. Чаты (3 минуты) — говорить на экране чата

## Текст

> Чат — это личные сообщения между пользователями в реальном времени, часть социального
> модуля. Задача была сделать не просто список сообщений, а переписку, которая работает
> мгновенно и при нескольких открытых вкладках.
>
> Первый вопрос при проектировании — как доставлять сообщения. Классический polling, то есть
> запрос «есть новое?» каждые несколько секунд, даёт задержку и лишнюю нагрузку, а статус
> «прочитано» через него неудобно показывать. Поэтому основным каналом взяли WebSocket: одно
> постоянное соединение, и сервер сам присылает клиенту, когда что-то произошло. HTTP-ручки
> для истории при этом остались — как резервный путь и для отладки через Swagger.
>
> Аутентификация. Браузерный WebSocket не умеет передавать заголовки, поэтому токен идёт
> в query-параметре. Сервер декодирует JWT, достаёт идентификатор пользователя и только
> после этого регистрирует соединение; если токена нет или он просрочен — соединение
> закрывается с кодом 1008.
>
> Дальше — реестр соединений. У человека может быть две вкладки и телефон, поэтому храним
> не один сокет на пользователя, а множество: сообщение уходит во все активные сессии.
> Если отправка в какой-то сокет падает, он выкидывается из реестра, остальные продолжают
> работать.
>
> Протокол явный: клиент присылает JSON с полем type — отправить сообщение, запросить
> историю, отметить прочитанным. Каждое событие описано Pydantic-схемой, поэтому контракт
> валидируется на входе, а некорректное событие возвращается как ошибка и не рвёт соединение.
>
> Отправка сообщения устроена так: сначала запись в базу, потом пуш получателю, если он
> онлайн, и эхо отправителю. Эхо нужно, чтобы в интерфейсе сообщение появлялось только после
> сохранения — без «фантомных» сообщений, которые потерялись по дороге.
>
> История листается курсором, а не через offset. Ключ — UUIDv7: он монотонно растёт со
> временем, поэтому сортировка по идентификатору это сортировка по времени. Скролл вверх
> не даёт дублей и пропусков и не съезжает, когда приходят новые сообщения.
>
> Прочитанность: один UPDATE, который обновляет только те сообщения, где получатель — это
> тот, кто читает, и которые ещё не прочитаны. Обновлённые группируются по отправителю,
> и каждому уходит событие read — клиент рисует галочки, не опрашивая сервер.
>
> По архитектуре всё как в остальном проекте: роутер тонкий, сервис держит правила — нельзя
> писать себе, нельзя тому, кто тебя заблокировал, — а репозиторий занимается только SQL.
> Один и тот же сервис обслуживает и HTTP, и WebSocket.
>
> Что осознанно не делали в MVP: реестр соединений живёт в памяти процесса, поэтому при
> нескольких инстансах бэкенда понадобится Redis pub/sub, а ещё нет heartbeat с таймаутами.
> Слои позволяют добавить это без переписывания.

## Версия на минуту

> Чат на WebSocket: постоянное соединение вместо polling, авторизация по JWT в
> query-параметре, потому что браузерный WebSocket не умеет заголовки. Реестр соединений
> хранит все вкладки пользователя, поэтому сообщение приходит во все. История листается
> курсором по UUIDv7, прочитанность — одним UPDATE с проверкой получателя. Всё идёт через
> общий сервис, одна логика для HTTP и WebSocket.

# Вопросы от разработчиков

**Почему тесты на моках, а не на реальной БД?**
> На моках они летают за доли секунды и проверяют логику, а не инфраструктуру. Реальную БД
> для интеграционных тестов надо поднимать отдельно — это следующий шаг.

**Почему стрики покрыты тестами, а чат нет?**
> Стрики — самая рискованная логика: границы, таймзоны, «сегодня ещё не отмечено». Ошибка там
> не падает, а тихо показывает неправильную цифру. WebSocket тестировать сложнее, его
> проверяли вручную двумя пользователями.

**Как считается стрик, если вчера отметил, а сегодня ещё нет?**
> Стрик не рвётся, пока не истёк срок `streak_expires_at` — он ставится на конец следующих
> суток. Пропуск целого дня рвёт стрик, отметка сегодня просто продлевает.

**Почему не покрыты права доступа между пользователями?**
> Есть тест на 401 без токена. Полная проверка изоляции требует двух пользователей в БД —
> это задача интеграционных тестов.

**Есть ли CI?**
> Нет, приоритет был отдать функционал. Есть pre-commit с форматированием; следующий шаг —
> GitHub Actions с прогоном `pytest` на каждый pull request.

**Что будет при двух репликах бэкенда?**
> Чат перестанет доходить до пользователей на другом инстансе — реестр соединений в памяти.
> Планировщик напоминаний начнёт дублировать сообщения. Лечится Redis pub/sub и отдельным
> воркером с блокировкой.

**Как накатываются изменения схемы БД?**
> Alembic, 14 миграций, применяются автоматически в entrypoint контейнера бэкенда.

**Где хранится состояние авторизации?**
> Access-токен — JWT на 7 дней, refresh-токены в БД отдельной таблицей, их можно отозвать.
> Пароли — Argon2.

**Что самое слабое место в проекте?**
> Отсутствие интеграционных тестов с настоящим Postgres и кэширования дашборда. Первое даёт
> уверенность в SQL, второе снимает нагрузку.

**Почему токен в URL у WebSocket?**
> Браузерный WebSocket не передать заголовки. Токен маскируется в логах фильтром, соединение
> живёт до истечения токена.

**Почему не отдаёте сообщения через offset?**
> При вставке новых сообщений страницы съезжают: дубли и пропуски. Курсор по UUIDv7 стабилен.

# Вопросы от бизнесменов

**Почему будут платить, если есть бесплатные трекеры?**
> Бесплатные дают список и напоминание. Мы продаём социальное обязательство и глубину:
> историю за всё время, сравнение периодов, отчёт, совместные привычки без ограничений.

**Сколько нужно пользователей, чтобы выйти в плюс?**
> Инфраструктура на одном Docker-хосте стоит немного, порог низкий. При цене 299 рублей
> и конверсии 2–3% каждый десяток тысяч активных пользователей даёт устойчивую выручку.
> Точные цифры будут после первых когорт.

**С кем конкурируете?**
> Ближайший аналог — Habitica: там тоже соцслой, но привычки живут внутри RPG-игры. У нас
> привычка живёт в ленте реальных друзей. Массовые трекеры вроде Streaks сильны в личном
> учёте, но социального обязательства не дают.

**Какая метрика успеха?**
> Отметки привычек в неделю на активного пользователя и удержание на 7-й день. Регистрации
> не показывают ценности.

**Как привлекаете первых пользователей?**
> Виральность внутри продукта: приглашение друга — часть механики. Плюс Telegram-бот как
> канал возврата туда, где человек уже сидит.

**Что мешает крупному игроку скопировать?**
> Экран скопировать можно, социальный граф и привычку людей — нет. Ценность растёт с числом
> друзей внутри продукта.

**Экономика: LTV и стоимость привлечения?**
> LTV считаем как ARPU, делённый на отток; на старте оттока ещё нет, поэтому опираемся на
> годовой тариф и бесплатный период. Привлечение на старте органическое.

**Юридически продажи готовы?**
> Нужны ИП или самозанятость, оферта и чеки по 54-ФЗ. Для первых продаж в боте проще
> Telegram Stars.

**Почему не B2B?**
> B2B — отдельный продукт с админкой, отчётами и SSO; на хакатоне это распыление. Тариф Team
> для пар и небольших групп ближе к нашей аудитории.

**Что если соцслой не зайдёт?**
> Остаётся платный слой на аналитике и экспорте: история, отчёты, сравнение периодов.
> Работает и без друзей, просто потолок выручки ниже.

**Дорожная карта после хакатона?**
> Сначала тарифы и платежи с лимитами, затем метрики воронки и показ paywall, потом
> командные привычки и дайджест в Telegram.

# Шпаргалка на карточку

- Продукт: соцсеть, где контент — привычки. Не трекер.
- Проблема: одиночные трекеры бросают, нет внешнего обязательства.
- Аудитория: 18–35, кто бросил трекеры; пары и друзья.
- Метрика: отметки в неделю, удержание D7, стрик 21 день.
- Монетизация: Free / Pro 299 ₽ / Team 599 ₽; платим за глубину, общение бесплатно.
- Тарифы в коде не реализованы — это следующий шаг, функции готовы.
- Тесты: 16, `poetry run pytest`, 0.2 с; 9 юнит (стрики, JWT, пароли, валидация),
  7 API (401/409/404/400/201).
- Не покрыто: Postgres-интеграция, WS, CSV.
- Цифры: 33 эндпоинта, 10 достижений, демо-база ~535 тыс. отметок.
- Фраза-страховка — про архитектуру, один раз.
